# gmcli

A Rust CLI (`gmcli`) that operators use to deploy and manage a gm subnet
miner. The miner itself is a containerized workload running inside an Intel TDX
TEE managed by Phala Cloud. This CLI handles the full operator lifecycle:
authentication, miner image build/push, Phala Cloud deployment, hash
verification against the registry's approval list, image registration, product
declaration, and price management.

## Layout

- `cli/src/main.rs` — clap surface plus the `dispatch` / `dispatch_worker` routers; pure coordination, no logic
- `cli/src/commands/` — one module per subcommand handler (`deploy`, `products`, `pricing`, `sources`, `hotkey`, `doctor`, `wizard`, `keys`, `earnings`, `fun`) plus `persist` (config/token persistence) and the shared `status_error`/`me_error` helpers in `commands/mod.rs`
- `cli/src/lib.rs` — module declarations; re-exports for binary and tests
- `cli/src/auth.rs` — Taostats device-code OAuth2 flow
- `cli/src/client.rs` — `RegistryClient`: typed HTTP wrappers for registry endpoints
- `cli/src/config.rs` — `Config` loaded from `~/.gmcli/config.json` (mode 0600); supports `mainnet`/`testnet` networks
- `cli/src/network.rs` — `Network` enum (testnet/mainnet) carrying `netuid`, chain websocket, and default registry URL; the seam later work (register-hotkey, earnings) reads coordinates from
- `cli/src/btcli.rs` — `BtcliBridge` trait + `RealBtcli`: bridge to `btcli` (bittensor-cli) for read-only wallet-list and metagraph queries; `gmcli` never signs an extrinsic or touches wallet keys — the operator runs any wallet-signing command themselves. `btcli_network()` maps `Network`→`test`/`finney`
- `cli/src/dependency.rs` — `ensure_dependency(&Dependency, assume_yes)`: reusable PATH-detect-and-offer-to-install primitive (e.g. `BTCLI`); `register-hotkey`'s assisted flow uses it, `deploy`/future init-wizard can adopt it
- `cli/src/register_hotkey.rs` — pure decision logic for `register-hotkey` (ss58 validation, bring-your-own vs assisted), testable against a stubbed `BtcliBridge`
- `cli/src/deploy/` — deploy orchestration split by responsibility: `mod.rs` (`prepare_deploy_target`, `ImageProvisioner`), `cvm.rs` (`PhalaClient` trait + `RealPhalaClient`, `phala deploy` / `phala cvms get`), `registry_auth.rs` (private-registry pull-credential probing), `compose.rs` (env/compose rendering), `version.rs` (image-version fetch/select), `hashes.rs` (hash normalize/verify)
- `cli/src/image.rs` — miner image build/push: `docker buildx --push` to a public registry, digest resolution
- `cli/src/node_secret.rs` — per-worker node secret: a fresh secret per worker (CVM), reused across re-deploys of the same `--app-name`, persisted in the worker's config record, embedded in compose env so envoy enforces it
- `cli/src/pricing.rs` — discount/price conversion, integer-only, no floats: `parse_discount_pct` (decimal-string → basis points), `PRICE_DIMENSIONS` (the one table of the ten price dimensions), `effective_dimensions` (percentage → absolute per-dimension vector), and the renderers `format_usd` (the one money formatter) / `effective_rate_summary` / `extra_dimension_lines`
- `cli/src/table.rs` — `render(headers, rows)`: the one text table, every column sized to its own widest cell. `status`, `pricing` and `sources` all go through it
- `cli/src/types.rs` — shared types: `Provider`, `Product`, `RetailDimensions` (the full per-dimension price vector), `MinerStatus`, and the worker request/response shapes (`WorkerCreateRequest`, `WorkerEntry`, `WorkerListResponse`)
- `azure-verify/` — `gm-azure-verify`: the Azure owner-capture checks, shared by `attestd` (fail-closed boot gate + periodic re-verification) and `gmcli doctor` (preflight). One crate on purpose: a doctor that promised a PASS the boot gate then refused would be worse than no preflight. `AzureVerifier::verify_target` is the gate's pass/fail; `audit_target` is the same sweep collecting every finding for doctor to print
- `image/` — the miner container image (Dockerfile, envoy config)
- `dstack/` — the compose template `gmcli deploy` renders and submits to Phala Cloud

## Build / lint / test

```bash
cd cli   # or from repo root

# build
cargo build --release -p gmcli

# lint
cargo clippy --all-targets --all-features -- -D warnings

# format check
cargo fmt --check

# tests (wiremock for registry HTTP; no real Phala Cloud / docker required)
cargo test -p gmcli
```

## Subcommands

| Command | Purpose |
|---|---|
| `init` | Guided onboarding wizard: register hotkey → login → set keys → deploy → declare products, skipping steps already done |
| `set-api-keys` | Persist provider API keys (Anthropic, OpenAI, Google, Chutes, Z.ai, Moonshot, DeepInfra, KubeTEE, Engy, Moonmath) and cloud-upstream selectors (Bedrock, Microsoft Foundry, Azure OpenAI) to `~/.gmcli/config.json` |
| `deploy` | Full trust-correct deploy: build/push image + Phala Cloud deploy + hash verification + image registration |
| `login` | Device-code OAuth flow; stores access token in config |
| `register-hotkey` | Record the serving hotkey: `--hotkey-ss58` records one registered elsewhere; otherwise (`--wallet`/`--hotkey`) resolves the local btcli hotkey, checks the metagraph, and prints the `btcli subnet register` command for the operator to run — gmcli never signs |
| `doctor` | Preflight checklist (network, login, provider keys, `phala` CLI + API key, Azure owner-capture controls, hotkey registration) with actionable fixes |
| `register-image` | Re-register an already-deployed image (debugging / registry resync; hidden from default help) |
| `declare-product` | Register a single miner-product offer with a pct discount — a catalog product, or a sourcing route from `sources` |
| `declare-products` | Fan one discount across the catalog (or one provider) |
| `undeclare-product` | Withdraw a single offer (catalog product or sourcing route); re-declaring re-offers it |
| `undeclare-products` | Withdraw every standing offer (`--all`) or one provider's slice (`--provider`) |
| `status` | Show current registration state, per-product eligibility, and the per-Mtok rate received; every ineligible offer is explained beneath the table with the registry's reason and the fix (`list-products` is a hidden alias) |
| `pricing` | Rank each offer against the eligible field on the scalar the gateway routes on — your rank, the field's size, its best/median cost, and the products others serve and you do not |
| `sources` | List the sourcing routes you can serve: a buyer product served from a cheaper upstream, with the buyer retail you settle on, how many of your workers currently serve it, and whether you already offer it |
| `earnings` | Read the hotkey's neuron row from the subnet metagraph (via btcli) and report UID, stake, and per-tempo emission |
| `update` | Replace this binary with the latest GitHub release via `axoupdater`, reading the install receipt cargo-dist's shell installer wrote. Takes no config and no token — a stale CLI is often a stale login too |
| `worker add/list/remove` | Manage the data-plane workers (Phala CVMs) attached to the hotkey |
| `publish-image-version` | Compute the release image's `compose_hash`/`os_image_hash` offline and upsert the approved `ImageVersion` to the registry (release pipeline; needs the registry admin key) |

Network selection is a sticky `--network testnet|mainnet` (mainnet by default);
`--testnet` is the shorthand. The `Network` profile (`cli/src/network.rs`)
carries each network's `netuid`, chain websocket, and default registry URL.

## Key conventions

- Anthropic offers can use the Anthropic API, AWS Bedrock, or Microsoft Foundry (an Anthropic-native passthrough at `https://<resource>.services.ai.azure.com/anthropic/v1/messages`, so envoy needs only the same host/path/header rewrite Bedrock uses). Cloud backends are single-slot and carry a registry `backend` marker; Foundry dispatches on the *deployment* name, declared per-offer with `--upstream-model`. `attestd` verifies each configured Azure account's owner-capture controls at boot and periodically, and `gmcli doctor` runs the same `gm-azure-verify` code as a preflight so the failure is caught before a CVM is paid for — see `AZURE_VERIFY_NOTES.md`, including what that verification does *not* cover. Azure attaches an Application Insights connection to a portal-created Foundry resource by default, and the gate refuses to boot while it exists: that is the single commonest Azure deploy failure.
- Prices are declared as a `--discount-pct` in `[0, 99.90]` with up to two decimal places. The CLI converts to integer basis-points (no floats) before sending to the registry. The miner receives `(100 - pct)%` of retail per Mtok.
- **A product's price is a ten-dimension vector, not an input/output pair.** `RetailDimensions` (`cli/src/types.rs`) mirrors `$defs/PriceDimensions` in the gm repo's `shared/schemas/product.json`: input and output required, then `cache_read`, `cache_write_5m`, `cache_write_1h`, `audio_input`, `audio_output`, `cache_storage_per_mtok_hour`, `long_context_input`, `long_context_output` — all nullable, null meaning "this model does not price it" (never zero). `long_context_threshold_tokens` rides alongside as a token count and is never discounted. `pricing::PRICE_DIMENSIONS` is the single table the arithmetic and every rendering walk, so adding a dimension is one row there plus one field on the struct; `pricing::every_price_dimension_is_wired_into_the_table` fails when the struct gains a field the table does not carry.
- `declare-product` / `declare-products` resolve `--discount-pct` into the **absolute** per-dimension figures client-side, print them, and confirm before any POST — a percentage is input ergonomics, not something a miner can price in their head. `--yes` (and a non-TTY stdin, via `dependency::confirm`'s default) skips the prompt so scripted declarations keep working. The wire body is still `{provider, model, discount_bp, upstream_model}` because the registry's schema is `additionalProperties: false`; when it accepts an absolute vector, the switch is one field on `ProductDeclarationRequest` plus the already-resolved `effective_dimensions` output at the two call sites in `commands/products.rs`.
- **The prompt asks about the percentage, not the figures, and `products::sent_as_lines` says why in the output.** The registry re-resolves the vector against its own retail when it records the offer, so retail moving between the catalog fetch and the POST leaves the miner paid on the registry's numbers — and the fan-out widens that window across N sequential requests. Wording the prompt as "declare at these prices?" would promise an atomicity the wire does not have. Closing the race fully needs the absolute vector on the wire *plus* a retail fingerprint the registry rejects when stale; neither is built.
- Only dimensions a product actually prices are rendered. `effective_rate_summary` carries the two anchors plus a `(+N more)` marker; `extra_dimension_lines` is the `retail → you receive` block beneath, and both `declare-product` and `status` use it. A two-dimension product renders exactly as it did before the vector landed.
- **`pricing::format_usd` is the only money formatter, and it never truncates.** Precision comes from the amount's own significant digits: nine places is exact for nano-dollars, trailing zeroes trim back to a minimum of three. There is deliberately no shorter variant to reach for — a fixed three places looks sufficient until the model is a cheap one, and then a real cost renders as `$0.000` (free) and two distinct rival costs render identically. That bit twice: first on the per-Mtok dimensions, then again on `gmcli pricing`'s YOUR COST / BEST / MEDIAN, which is the *one* view whose job is deciding what to charge. Do not reintroduce a tiered or fixed-width money formatter anywhere.
- **Every table goes through `cli/src/table.rs::render`, which sizes each column from its own widest cell.** `status`, `pricing`'s rank table and `sources` each had hand-picked widths chosen against a `$3.000` example; once prices stopped truncating, a cheap model's cell (`$0.000894999 in / $0.000000894 out per Mtok (+8 more)`, 53 chars in a 12- or 44-wide column) pushed the trailing columns off their headers. Do not reintroduce a fixed-width column.
- **A declined confirmation is not a success.** `cmd_declare_products` returns `DeclareOutcome::Cancelled` rather than `Ok(())` when the miner says no, because `gmcli init` goes on to claim the step is done. `cmd_declare_product` deliberately does not carry the outcome: `dispatch` is its only caller and a CLI run asked to do nothing exits 0.
- **`gmcli init`'s closing banner is derived, never assumed.** Every step returns `StepOutcome::{Done, Outstanding(command), Stop}`; `run_steps` collects the outstanding commands and `closing_lines` decides the summary from that list. "All set" is printed only when the list is empty. This defect — a skip notice immediately followed by a success banner — survived three fixes aimed at the *message*, so fix the flow: a step that was skipped, declined, or short of its input is `Outstanding` and carries the command that finishes it. `closing_lines` is pure and asserted on directly, and the assertion that matters is the *absence* of the banner (asserting the skip line alone passes against the bug). Synthetic `StepOutcome`s pin `closing_lines` but not what feeds it, so the step functions are also driven for real with `assume_yes` (which short-circuits the same prompts a non-TTY stdin does) — five of the six mappings, plus `run_steps` end to end. Only the two paths behind a live TTY answer (a declined price confirmation, and the macro's `Skip` arm) are uncovered.
- **Assert every rendered row, never the rule against the header.** All three tables had a `the_rule_is_exactly_as_wide_as_a_row` test that compared the rule to the *header* only — which passes however far the data rows overflow, and is precisely why the fixed widths went unnoticed. The invariant is that header, rule and every row are the same width; `table::tests::assert_uniform` is the shape to copy.
- **Check a new test fails against the defect it names, and that it fails for the right reason.** Two ways they don't: `contains("$0.268")` is satisfied by both the correct `$0.2685` and the truncated `$0.268` (match to the end of the line instead), and a fixture can trip a width assertion via some cell other than the one under test (the rank-table test detected a re-capped 12-char cost column only because its model id happened to exceed the old 32-char model width). State the calibration in the test when it matters.
- Table widths count Unicode scalars, which is what `{:<width$}` pads by, so rows stay self-consistent whatever the cells hold; that equals *terminal* columns only because every cell is ASCII (provider is an enum, the model id is a provider API identifier that must survive URL-path interpolation). `product.json` puts no `pattern` on the model field, so it is a catalog property, not a contract guarantee — a wide-glyph slug would misalign columns and nothing worse, which does not justify a `unicode-width` dependency. A test pins the ASCII assumption.
- A supplier route is one of possibly several upstreams that serve a buyer product (e.g. `deepinfra/zai-org/GLM-5.2` and `engy/glm-5.2` both serve `zai/glm-5.2`); none is canonical, and the buyer product id names the model, not the host. Every offer has an explicit route, including a self route. The gateway filters route candidates for the request, keeps the cheapest surviving route per worker, and gives that worker one lottery entry. Source products are filtered out of buyer-facing `GET /products`; `sources` reads all declarable routes from `GET /miners/products/routes` and falls back to the older cross-product endpoint for display only. Settlement is on the *buyer* product's retail less the declared discount. `declare-products` declares only catalog products backed by self routes; alternate supplier routes remain deliberate single declarations.
- **Adding a supplier (a new upstream provider) touches two repos, and `docs/sourcing.md` is the step that gets forgotten.** In this repo: the `Provider` enum (`cli/src/types.rs`), the key field and accessor (`cli/src/config.rs`), the slot fan-out (`cli/src/slots.rs`), the `set-api-keys` flag (`cli/src/main.rs`), the envoy route + cluster + SNI (`image/envoy.yaml`), the key guard and `fan_out_slots` call (`image/start.sh`), the compose env passthrough (`dstack/docker-compose.yaml`), `CANONICAL_ALLOWED_ENVS` and its length in `cli/src/compose_hash.rs`, and — if the supplier serves an existing buyer product rather than its own — a row in the `docs/sourcing.md` matrix plus the provider list in `README.md` §3 and the `set-api-keys` row above. Adding an allowed env changes the attested `compose_hash`: update the deterministic render golden in the code change, but keep the registry-approved hash gate red until the new image is built, published, and approved; never replace that anchor with an unapproved locally computed hash. In the `gm` repo: the upstream route seed/migration, the curated price tables (keyed by `(provider, model)` — a bare model id is not unique across upstreams), the `product.json` provider enum (then codegen), and the control-loop probe tables. GM's CI fails if a source-route pair is missing from this repo's `docs/sourcing.md`, so the docs step is enforced — but only for sourcing routes, not for a supplier that gets its own buyer product.
- Withdrawing an offer (`undeclare-product`, or the `undeclare-products` fan-out over the offers still standing in `GET /miners/me`) keeps the registry row for audit — `is_offered=false`, reason `withdrawn_by_miner` — rather than deleting it, and is fully reversible by re-declaring; that reversibility is why neither command asks for confirmation.
- Each worker (Phala CVM) carries its own node secret, generated fresh on first deploy and reused on re-deploys of the same `--app-name`. The secret is embedded in the compose env, enforced by envoy, and stored in the registry — all three must stay in lockstep across re-deploys.
- Worker #1 (the worker `deploy` / `register-image` refresh via `POST /miners/register`) is the **oldest live worker in the registry**, read from `GET /miners/{hotkey}/workers` — never a local record's position. Local `WorkerRecord`s are not pruned when the registry deregisters a worker, so a dead CVM can sit at local position 1 forever. `workers::is_secondary_live` is the one place that decision is made.
- `phala deploy` cannot reuse a CVM name, so `deploy` / `worker add` probe for an existing CVM under `--app-name` before any image build and stop with the `phala cvms delete <app_id>` to run. gmcli never deletes a CVM: that destroys a running worker and stays the operator's explicit act.
- `--network` / `--testnet` are sticky: an explicit choice is persisted as `active_network`, so later commands target it until a different one is passed. `--api-url` is *not* sticky — it overrides the registry URL for a single run only (as does `GM_REGISTRY_URL`).
- `deploy` is the happy path: it verifies that the deployed compose hash and OS image hash exactly match the registry's approved version before registering the image. `register-image` exists only for re-registration without redeploying.
- Config file is at `~/.gmcli/config.json` (mode 0600). The `GM_REGISTRY_URL` env var can override the API URL for a single run without persisting.
- `deploy` and `register-image` shell out to the `phala` CLI (npm package `phala`, install with `npm i -g phala`). Phala Cloud auth uses a Phala Cloud API key: pass `--phala-api-key`, set `PHALA_API_KEY` / `PHALA_CLOUD_API_KEY`, or `phala auth login` for a CLI session. The `phala` CLI is preflighted at the start of `deploy` with an install hint.
- `update` is the only command that rewrites the binary on disk. It refuses when the install receipt does not describe the running executable (a `cargo build` copy alongside an installed one): axoupdater's own answer there is "no update needed", which reads as "you are current" when the truth is "not upgradable this way". `dist-workspace.toml` deliberately does NOT set `install-updater` — that would ship a second, standalone `gmcli-update` binary doing the same job.
- **gmcli ships inside the miner image too** (`image/Dockerfile`), because `start.sh` shells out to the hidden `slot-env` to derive upstream key slots — so the CLI is load-bearing in the TEE and cannot be dropped from it. `update` goes along with it and is deliberately not gated out: the image installs the binary by `COPY`, never through the shell installer, so no install receipt exists there and the command fails closed on its own. The awkwardness is that `cli/src/slots.rs` is a pure library living in a binary; extracting it into a crate shared with `attestd` (the way `azure-verify` already is) would be the real fix, and would let the image drop the CLI entirely.
- Releases are cut with `./scripts/release.sh`, which derives the tag from `[workspace.package] version` rather than taking it as an argument. Never hand-tag: `dist` refuses a tag that does not match the workspace version, and five tags (`v0.3.11-dev` through `v0.3.14`) were pushed against a stale `Cargo.toml` and silently published nothing. The bump itself is an ordinary reviewed PR — the script only tags, so nothing pushes to `main`.
- Supply-chain: workspace `deny.toml` governs advisory/license/ban checks (`cargo deny check`).
